# 비상로지스 기능 개발 오케스트레이터

## 실행 모드

**에이전트 팀 (파이프라인 아키텍처).** 이 환경에는 전용 `TeamCreate` 도구가 없으므로, 팀은 다음으로 구성한다:

- `Agent` 도구로 이름을 지정해 `supabase-schema-agent` → `nextjs-builder-agent` → `qa-verifier-agent`를 스폰한다(모두 `model: "opus"` 명시, 필요에 따라 `run_in_background`).
- `TaskCreate`로 세 단계를 의존관계 있는 작업으로 등록해 진행 상황을 추적한다.
- 각 에이전트 정의(`.claude/agents/*.md`)의 "팀 통신 프로토콜"에 따라 에이전트끼리 `SendMessage`로 직접 소통하게 한다(핸드오프, 불일치 보고). 오케스트레이터는 태스크 상태를 모니터링하고 최종 결과를 사용자에게 종합 보고한다.

## Phase 0: 컨텍스트 확인

1. `비상로지스_PRD.md`를 읽어 요청과 관련된 섹션(5장 데이터 모델 / 6장 Phase / 7장 화면 명세 / 4장 공통 규칙)을 확인한다.
2. `git status`, `git log --oneline -5`로 커밋되지 않은 이전 작업이 있는지 확인한다 — 있다면 먼저 사용자에게 처리 방향(커밋/폐기/이어서 작업)을 확인한다.
3. 요청이 PRD의 특정 Phase(6장)에 대응하면 해당 Phase의 하위 작업 목록을 그대로 작업 단위로 쓴다. PRD에 없는 요청(버그 수정, 임의 개선)이면 요청을 스키마 변경 필요 여부로 먼저 분류한다.
4. 이전 실행의 `_workspace/`가 있고 사용자가 부분 수정을 요청했으면 해당 단계 에이전트만 다시 호출한다(전체 파이프라인 재실행 금지).

## Phase 1: 작업 분해 및 팀 구성

1. 요청을 스키마 변경 필요 여부로 분류한다:
   - 새 컬럼/테이블/RPC 필요 → 3단계 전체 파이프라인(schema → builder → qa)
   - 기존 스키마로 화면/로직만 추가 → builder → qa (schema 단계 생략)
   - 순수 버그 수정 → 버그 위치(스키마/프론트)에 맞는 단계만 호출, qa는 항상 포함
2. 독립적인 여러 Phase/기능을 동시에 요청받았고 서로 데이터 의존이 없으면(예: PRD 6장의 Phase 6 세금계산서와 Phase 7 엑셀 가져오기는 서로 독립적) 파이프라인을 병렬로 여러 개 돌린다(팬아웃). 의존이 있으면(예: 계산서 발행은 `settings`의 팝빌 on/off 설정에 의존) 순서를 지킨다.
3. `TaskCreate`로 각 파이프라인의 단계를 의존관계로 등록한다.

## Phase 2: 실행

1. `supabase-schema-agent`를 스폰(필요한 경우)해 마이그레이션/RPC를 작성·적용시킨다.
2. 완료되면(SendMessage로 계약 전달 확인 후) `nextjs-builder-agent`를 스폰해 화면/서버 액션을 구현시킨다.
3. 완료되면 `qa-verifier-agent`를 스폰해 실제 Supabase 프로젝트 기준으로 경계면 검증 + PRD 4.3 수치 검증 + `tsc --noEmit`을 수행시킨다.
4. QA가 불일치를 발견해 스키마/빌더 에이전트에게 되돌리면(팀 통신 프로토콜), 해당 에이전트가 수정 후 QA에게 알리고 QA는 해당 항목만 재검증한다. 오케스트레이터는 이 왕복이 2회를 넘기면 개입해 사용자에게 상황을 보고한다.

## 데이터 전달 프로토콜

| 전략 | 내용 |
|------|------|
| 파일 기반 (주 전달 수단) | 마이그레이션 SQL, `actions.ts`, 컴포넌트 파일 — 실제 산출물 |
| 메시지 기반 | 에이전트 간 계약 전달·불일치 보고는 `SendMessage` |
| 태스크 기반 | `TaskCreate`/`TaskUpdate`로 오케스트레이터가 전체 진행 상황 파악 |

파이프라인을 2개 이상 병렬로 돌릴 때는 각 파이프라인의 중간 결과를 `_workspace/{phase}_{agent}_{artifact}.md`에 짧게 남겨 사후 추적이 가능하게 한다(예: `_workspace/phase5_schema_contract.md`).

## 에러 핸들링

- 각 단계는 실패 시 1회 재시도. 같은 원인으로 재실패하면 해당 파이프라인을 중단하고 사용자에게 구체적 원인과 함께 보고한다(다른 독립 파이프라인은 계속 진행).
- PRD와 충돌하거나 불명확한 요구사항은 에이전트가 임의로 판단하지 않고 오케스트레이터를 거쳐 사용자에게 질문한다(PRD 코딩 에이전트 실행 요청문 6항).
- 금액 규칙(PRD 4.3) 검증이 실패하면 다른 어떤 이유로도 진행하지 않는다 — 이 프로젝트의 최우선 요건.

## 완료 후

1. 변경 사항을 논리적 단위로 커밋할지 사용자에게 먼저 확인한다(임의로 커밋하지 않음).
2. 사용자에게 개선 피드백을 받을 기회를 제공한다("결과에서 바꾸고 싶은 부분이 있나요?"). 피드백은 이 프로젝트 `CLAUDE.md`의 변경 이력에 기록하고 해당 에이전트/스킬을 갱신한다.

## 테스트 시나리오

- **정상 흐름**: "배차 등록 폼에 '적재함 종류' 필드 추가해줘" → schema-agent가 컬럼+RPC 갱신 → builder-agent가 폼/목록에 반영 → qa-verifier-agent가 실제 DB로 저장/조회 검증 → 통과 보고.
- **에러 흐름**: qa-verifier-agent가 RPC 파라미터 순서 불일치를 발견 → schema-agent에게 재현정보 전달 → schema-agent가 마이그레이션 추가로 수정 → qa-verifier-agent가 해당 항목만 재검증 → 통과.
